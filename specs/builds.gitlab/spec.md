# Збірки з пайплайнів GitLab за посиланням

> Частина [основної специфікації](../SPEC.md), розділ [3. Пристрій і сесія](../SPEC.md#device). Принципи продукту — у [розділі 13](../SPEC.md#rules), правила роботи з кодом — в [AGENTS.md](../../AGENTS.md); тут вони не повторюються.

- **ID:** `builds.gitlab`
- **Статус:** implemented
- **Етап за документом:** MVP (вибір білда з GitLab-артефактів)
- **Як зроблено:** [design.md](design.md)

## Проблема й користувач

QA отримує посилання на пайплайн, чекає, поки збереться збірка, завантажує артефакти, шукає в архіві потрібний файл і ставить його. Пайплайни різних проєктів збирають у різних джобах, а для симулятора й реального пристрою потрібні різні збірки. Станція бере посилання й робить решту сама.

## Критерії приймання

1. **Дано** посилання на пайплайн чи джобу будь-якого проєкту на налаштованому GitLab (вставлене в поле чи ⌘V будь-де на «Збірках»), **тоді** станція читає пайплайн, його джоби й джоби пайплайнів, які він запускає (bridges).
   Тест: `test/unit/pipelines.spec.js`, `test/unit/gitlab-pipeline.spec.js`
2. **Дано** посилання на інший GitLab, ніж налаштований, або пайплайн, якого токен не бачить, **тоді** станція пояснює це й не опитує далі.
   Тест: `test/unit/gitlab-pipeline.spec.js`
3. **Дано** правила в Налаштування → Збірки (проєкт за шляхом, його кінцем чи шаблоном із `*`; для симулятора/емулятора й для реального пристрою — джоби за пріоритетом і шаблон файлу), **тоді** для посилання береться найточніше правило; для реального пристрою без своїх джоб беруться джоби симулятора.
   Тест: `test/unit/pipelines.spec.js`
4. **Дано** проєкт без правила, **тоді** на картці пайплайна відкривається редактор правила з джобами цього пайплайна (ті, що схожі на збірку, позначені); збережене правило діє й для наступних пайплайнів.
   Тест: `test/unit/pipeline-watch.spec.js`
5. **Дано** джобу, що виконується, **тоді** станція чекає й питає GitLab кожні 10 с; ручну джобу можна запустити кнопкою; джоби, яких ще немає в пайплайні, що триває, — теж чекає.
   Тест: `test/unit/pipelines.spec.js`, `test/unit/pipeline-watch.spec.js`
6. **Дано** джобу, що завершилась зі збіркою, **тоді** станція завантажує артефакти й бере з архіву збірку для типу пристрою: APK для Android, теку `.app` для симулятора, IPA для iPhone, ніколи AAB; з урахуванням шаблону файлу, вибору минулого разу (з іншим номером збірки) й universal.
   Тест: `test/unit/pipelines.spec.js`
7. **Дано** кілька підходящих збірок в архіві, **тоді** станція питає, яку взяти, і запамʼятовує вибір для проєкту.
   Тест: `test/unit/pipeline-watch.spec.js`
8. **Дано** цільові пристрої різних типів (симулятор і реальний iPhone), **тоді** кожен тип отримує свою збірку зі своєї джоби й свої встановлення.
   Тест: `test/unit/pipeline-watch.spec.js`
9. **Дано** «Поставити, щойно буде готово», **тоді** готова збірка ставиться на обрані пристрої з дозволом на нижчу версію; для іншого підпису є «Перевстановити»; встановлений на активному пристрої застосунок стає активним; приходить сповіщення (системне, якщо вікно сховане).
   Тест: `test/unit/pipeline-watch.spec.js`
10. **Дано** незавершені пайплайни, **коли** станцію перезапущено, **тоді** вони відстежуються далі; завершені — ні.
    Тест: `test/unit/pipeline-watch.spec.js`

## Поведінка й інтерфейс

- Картка пайплайна: проєкт, номер, гілка, стан; «Куди ставити» (кілька пристроїв), «Поставити, щойно буде готово»; рядок для кожного типу пристрою з джобою, станом, прогресом, збіркою й встановленнями; «Правило: … · змінити».
- Опитування йде, хоч би яка вкладка відкрита.

## Безпека й приватність

Токен GitLab у Keychain: `read_api` для читання й артефактів, `api` для запуску ручних джоб. Посилання на інші сайти відхиляються, токен туди не йде.

## Метрика корисності

Збірки, встановлені з пайплайнів без ручних кроків.

## Відкриті питання

- Пайплайн збірки, запущений trigger token з іншого проєкту, не повʼязаний із пайплайном, що його запустив; вставляти треба посилання на сам пайплайн збірки.
- Перевірити з реальним GitLab банку.
