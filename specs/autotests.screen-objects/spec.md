# Screen object з екранів сесії

> Частина [основної специфікації](../SPEC.md), розділ [6. Інспектор і автоматизація](../SPEC.md#inspector); стосується також: [4. Телеметрія](../SPEC.md#telemetry) ([inspector.flow](../inspector.flow/spec.md)), [15. Агент станції](../SPEC.md#agent). Принципи продукту — у [розділі 13](../SPEC.md#rules), правила роботи з кодом — в [AGENTS.md](../../AGENTS.md); тут вони не повторюються.

- **ID:** `autotests.screen-objects`
- **Статус:** implemented
- **Етап за документом:** v1 (Page Object генератор)
- **Як зроблено:** [design.md](design.md)

## Проблема й користувач

QA проходить застосунок у сесії, і станція вже знає кожен екран і його стани ([inspector.flow](../inspector.flow/spec.md)): дерево, локатори, скриншот. Автоматизатор потім проходить ті самі екрани ще раз, щоб написати screen object руками. Після сесії все зібране зникає, бо живе лише в пам'яті.

Ця фіча дає наприкінці сесії побачити екрани, обрати потрібні стани (окремо чи об'єднавши стани одного екрана), зберегти їх у проєкті й отримати код screen object на Kotlin за правилами команди з репозиторію автотестів ([project.autotests](../project.autotests/spec.md)). Готовий результат забирає агент тестів ([access.external-agents](../access.external-agents/spec.md)). Станція в репозиторій автотестів не пише.

Станція нічого не відбирає: у screen object потрапляють усі елементи стану, кожен із локатором і методами взаємодії. Що з цього лишити, людина вирішує вже в коді, в іншому процесі (агент тестів, ревю). Код пише модель за правилами команди. Детермінований скрипт генерації замість моделі — наступний крок, коли правила для Android та iOS буде описано.

## Критерії приймання

Підсумок сесії

1. **Дано** сесію з екранами, що мають назву, **коли** її зупинено чи на робочому столі почато «Новий тест», **тоді** станція відкриває «Підсумок для автотестів»: екрани сесії з їхніми станами й мініатюрами. Ті самі екрани вдруге сам підсумок не пропонує. Відкрити його можна й посеред сесії кнопкою «Для автотестів» у стрічці екранів.
   Тест: немає (перевірено наживо з підкладеними екранами)
2. **Дано** підсумок, **тоді** екрани без назви ([inspector.flow](../inspector.flow/spec.md), критерій 8) у ньому не обираються, а під списком сказано, скільки їх: у screen object потрапляють лише екрани з назвою.
   Тест: `test/unit/autotests-screen-objects.spec.js`
3. **Дано** підсумок з обраними станами, **коли** користувач закриває його, нічого не зберігши, **тоді** станція попереджає, що екрани сесії буде втрачено, і питає.
   Тест: немає (перевірено наживо)

Одиниця й об'єднання

4. **Дано** екран зі станами, **тоді** за замовчуванням кожен обраний стан — окремий screen object.
   Тест: `test/unit/autotests-screen-objects.spec.js`
5. **Дано** два чи більше обраних станів **одного** екрана, **коли** користувач тисне «Об'єднати», **тоді** вони стають одним screen object: у нього входять елементи всіх станів, по разу, а елемент, якого немає в кожному стані, позначено назвами станів, де він є. Стани різних екранів не об'єднуються. Об'єднання можна розібрати назад.
   Тест: `test/unit/autotests-screen-objects.spec.js`
6. **Дано** screen object, **тоді** його назва береться з назви екрана (і стану, якщо він окремий): `com.bank.LoginActivity` → `LoginActivity`. Її можна змінити й до збереження, і після. Дві однакові назви в пакеті отримують номер.
   Тест: `test/unit/autotests-screen-objects.spec.js`

Усі елементи, без відбору

7. **Дано** стан екрана, **тоді** у screen object потрапляють усі його елементи без відбору станцією; у підсумку їх не прибирають і не обирають. Для кожного елемента станція сама, без моделі, дає до трьох локаторів від найкращого (accessibility id, id, UiAutomator чи predicate і class chain, XPath) і дії, які з ним можна зробити: тап, введення й очищення тексту, позначка, прокрутка, читання тексту, перевірка видимості. Методи взаємодії з цього пише модель за правилами команди.
   Тест: `test/unit/autotests-elements.spec.js`

Збереження

8. **Дано** обрані screen object, **коли** користувач тисне «Зберегти», **тоді** станція зберігає їх в активному проєкті як пакет: назва, дата, пристрій і платформа, застосунок і версія, для кожного screen object — стани зі зменшеним скриншотом і всі елементи з локаторами й діями. Пакет переживає перезапуск станції.
   Тест: `test/unit/autotests-packages.spec.js`
9. **Дано** збережені пакети, **тоді** їх видно списком у блоці «Автотести» проєкту, найновіші першими; пакет можна відкрити й видалити. Пакети лежать окремо від налаштувань і не потрапляють в їхній експорт.
   Тест: `test/unit/autotests-packages.spec.js`

Генерація

10. **Дано** пакет і репозиторій автотестів із правилами ([project.autotests](../project.autotests/spec.md)), **коли** користувач тисне «Згенерувати код», **тоді** модель (Kiro, як в [agent.core](../agent.core/spec.md)) в окремій разовій розмові в репозиторії автотестів отримує правила, де лежать приклади, і всі елементи кожного screen object, а повертає код на Kotlin. Як і в чаті, потрібна згода проєкту й «так» понад денний поріг кредитів. Скриншоти моделі не йдуть.
    Тест: `test/unit/autotests-screen-objects.spec.js` (що йде моделі), `test/unit/agent-sessions.spec.js` (разова розмова)
11. **Дано** генерацію, **тоді** модель може читати репозиторій автотестів, але все, що потребувало б людини (запис у файли, інша команда), станція відхиляє сама. Код модель повертає у відповіді, а станція зберігає його в пакеті поруч зі screen object.
    Тест: `test/unit/agent-sessions.spec.js`, `test/unit/autotests-screen-objects.spec.js` (розбір відповіді)
12. **Дано** згенерований код, **тоді** користувач бачить його поруч зі станами екрана, може скопіювати, перегенерувати окремий screen object (за бажанням з уточненням словами) і позначити пакет «Готово для автотестів». Відповідь без коду показується як є.
    Тест: немає (перевірено наживо з підставним Kiro)
13. **Дано** правила чи репозиторій, яких немає, **тоді** генерація не стартує, а станція каже, чого бракує й де це вказати.
    Тест: `test/unit/autotests-packages.spec.js` (чого бракує)

## Поведінка й інтерфейс

- «Підсумок для автотестів» — бічна панель: назва пакета, екрани зі станами (мініатюра, галочка, назва screen object), смужка «Обрано станів екрана …: N. Зробити з них один screen object?» з «Об'єднати», «Розібрати» біля об'єднаного, внизу — у який проєкт піде пакет, «Закрити» і «Зберегти (N)».
- Пакет відкривається вікном: зліва screen object, справа — його назва, стани зі скриншотами, код і поле «Що змінити в коді цього screen object» з «Перегенерувати».

## Безпека й приватність

- Перед відправленням моделі тексти й локатори елементів проходять те саме приховування, що й в [ai.screen-check](../ai.screen-check/spec.md) (критерій 2): номери карток, IBAN, телефони, email, шаблони користувача.
- Пакети лежать лише в теці даних станції на цьому Mac.

## Метрика корисності

Кількість збережених пакетів і згенерованих screen object; частка пакетів, які забрав агент тестів.

## Відкриті питання

- Android та iOS: як зводити той самий екран з обох платформ в один screen object. Поки це вирішує модель за правилами команди; правила користувач опише пізніше, тоді ж — детермінований скрипт генерації замість моделі.
- Межі сховища: скільки пакетів і місця на проєкт (орієнтир — 50 МБ, як у кроці 2 [inspector.flow](../inspector.flow/spec.md)). Поки межі немає, пакети видаляє людина.
- Повне дерево кожного стану в контексті моделі коштує кредитів: якщо генерація пакета виходить дорогою, ділити її на screen object по одному.
- Нова сесія без зупинки попередньої (підʼєднання до іншої) починає екрани заново, не пропонуючи підсумку.
- Чи робить ця фіча зайвим «крок 2» [inspector.flow](../inspector.flow/spec.md) (карту застосунку на диску), чи пакети стануть його частиною.
